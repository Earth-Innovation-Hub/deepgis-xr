# TileServer URL Malformation Issue - Analysis & Fix

## Problem Summary

The DeepGIS application was failing to load raster tiles from `mbtiles.deepgis.org`, showing errors like:
- "Error: Successfully retrieved [URL] but it contained no content"
- "Memory error loading BF_08-02-2020 raster"
- TypeError related to image loading

**Root Cause**: The TileServer GL metadata contained malformed URLs with double protocols.

## Root Cause Analysis

### The Malformed Metadata

When fetching metadata from `https://mbtiles.deepgis.org/data/bf_aug_2020_raster.json`, the response contains:

```json
{
  "tiles": [
    "https://localhost:8091/data/bf_aug_2020_raster/{z}/{x}/{y}.png",           ✅ Valid
    "https://mbtiles.deepgis.org/data/bf_aug_2020_raster/{z}/{x}/{y}.png",     ✅ Valid
    "https://http://mbtiles.deepgis.org/data/bf_aug_2020_raster/{z}/{x}/{y}.png",  ❌ MALFORMED
    "https://https://mbtiles.deepgis.org/data/bf_aug_2020_raster/{z}/{x}/{y}.png"  ❌ MALFORMED
  ]
}
```

**Issue**: The last two URLs have double protocols:
- `https://http://` (https followed by http)
- `https://https://` (https followed by https)

### Why This Breaks Tile Loading

The application's URL selection logic was:

```javascript
let tileUrl = metadata.tiles.find(url => url.startsWith('https://mbtiles.deepgis.org'));
```

**The Problem**:
1. The string `"https://http://mbtiles.deepgis.org/..."` DOES NOT start with `"https://mbtiles.deepgis.org"`
2. It starts with `"https://http://"`
3. BUT, `new URL("https://http://mbtiles.deepgis.org/...")` technically succeeds because browsers interpret `http://mbtiles.deepgis.org` as the hostname
4. When tiles are requested with these malformed URLs, they either fail silently or return empty responses

### Difference from TileServer Main Interface

**Why the TileServer web interface works:**
- The TileServer GL web viewer at `mbtiles.deepgis.org` likely:
  1. Uses the **second** URL in the array (the valid one)
  2. Has built-in fallback logic that tries multiple URLs
  3. Filters URLs more strictly before attempting requests

**Why the application failed:**
- The URL selection picked a malformed URL in some cases
- No validation to filter out double-protocol URLs
- No fallback mechanism to try alternative URLs

## The Fix

### Changes Made

#### 1. Leaflet Implementation (`map_label.html`)

Added URL validation for both vector and raster layers:

```javascript
// Filter out malformed URLs (double protocols)
const validUrls = metadata.tiles.filter(url => {
    try {
        // Test URL by replacing template variables
        const testUrl = url.replace('{z}', '0').replace('{x}', '0').replace('{y}', '0');
        new URL(testUrl); // Will throw if malformed
        // Check for double protocol issue
        return !testUrl.includes('://http://') && !testUrl.includes('://https://');
    } catch (e) {
        console.warn('Filtered out malformed tile URL:', url);
        return false;
    }
});

// Use the first valid HTTPS URL from mbtiles.deepgis.org
let tileUrl = validUrls.find(url => url.startsWith('https://mbtiles.deepgis.org'));
if (!tileUrl) {
    // Construct a URL using the standard format
    tileUrl = `https://mbtiles.deepgis.org/data/${mbtilesId}/{z}/{x}/{y}.png`;
}
```

#### 2. Cesium Implementation (`layers.js`)

Enhanced existing URL validation with double-protocol check:

```javascript
const validUrls = metadata.tiles.filter(url => {
    try {
        const testUrl = url.replace('{z}', '0').replace('{x}', '0').replace('{y}', '0');
        new URL(testUrl);
        // Check for double protocol issue
        if (testUrl.includes('://http://') || testUrl.includes('://https://')) {
            console.warn(`[LayerUtils] Skipping URL with double protocol: ${url}`);
            return false;
        }
        return true;
    } catch {
        console.warn(`[LayerUtils] Skipping malformed tile URL: ${url}`);
        return false;
    }
});
```

### What the Fix Does

1. **Validates all URLs** in the metadata `tiles` array
2. **Filters out malformed URLs** before selecting one to use
3. **Checks for double protocols** specifically (the main issue)
4. **Logs warnings** when malformed URLs are detected
5. **Falls back to constructing a URL** if no valid URLs are found

## Upstream Issue: TileServer GL Configuration

### Where the Malformed URLs Come From

The malformed URLs are generated by TileServer GL, likely due to:

1. **Misconfigured domain/protocol settings** in TileServer GL config
2. **Multiple proxy layers** prepending protocols incorrectly
3. **Environment variable issues** where protocol is included in domain name

### Recommended Server-Side Fix

The TileServer GL configuration (wherever it's hosted) should be fixed to only output valid URLs. Check:

1. TileServer GL config file (usually `config.json`)
2. Environment variables like `PUBLIC_URL`, `DOMAIN`, etc.
3. Nginx/proxy configuration that might be adding extra protocols

**Example of what might be wrong:**

```json
// BAD - includes protocol in domain
{
  "domains": [
    "http://mbtiles.deepgis.org",
    "https://mbtiles.deepgis.org"
  ]
}

// GOOD - domain only, no protocol
{
  "domains": [
    "mbtiles.deepgis.org"
  ]
}
```

## Summary

**What was different between the calls:**
- TileServer main interface: Uses first valid URL or has better fallback logic
- Application: Was potentially selecting malformed URLs with double protocols

**What we fixed:**
- Added comprehensive URL validation
- Filter out malformed URLs before selection
- Added specific check for double-protocol issue
- Ensured fallback to constructing valid URLs

**What should be fixed upstream:**
- TileServer GL configuration to stop generating malformed URLs
- Check proxy/nginx configuration for protocol handling issues
